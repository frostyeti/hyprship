# Implementation Plan: Issue 1 (Setup Configuration/Viper & Gin)

## 1. Overview
This document outlines the implementation plan for [Issue #1](https://github.com/frostyeti/hyprship/issues/1) to introduce `gin` for HTTP routing and `viper` for application configuration in the `apps/api` project. Logging will be explicitly deferred to a later issue.

## 2. Dependencies
- Navigate to the `apps/api` project.
- Run `go get github.com/spf13/viper` and `go get github.com/gin-gonic/gin` to fetch the latest versions.
- Run `go mod tidy` or use the `cast tidy` task to ensure the `go.mod` is properly updated.

## 3. Configuration (Viper)
- **Struct Definitions**: Create the foundational configuration structures in `apps/api/config/config.go` (or similar):
  ```go
  type Config struct {
      Log  *LogSettings
      Port int
      Env  string
      Addr string
  }

  type LogSettings struct {
      Level string
  }
  ```
- **Viper Setup**:
  - Configure Viper to read from YAML, TOML, environment variables, and command-line flags.
  - Set the environment variable prefix to `HYPRSHIP`. Allow this prefix to be overridden if needed.
  - Use the configuration to set up Gin (e.g., set `gin.SetMode(gin.ReleaseMode)` if `Env` is not "development").

## 4. Route Implementation
- **Response Envelope**: Implement the standard API response envelopes according to `apps/api/AGENTS.md` in a shared package (e.g., `apps/api/routes/response.go`):
  - `ApiError`
  - `ApiErrorDetail`
  - `Response` wrapper ensuring `Ok` and `Value` are present.
- **Endpoints**:
  - `GET /api/v1/ping`: Implement to return the standard envelope: `{"value": "pong", "ok": true}`.
  - `GET /api/v1/healthz`: Implement a standard health check endpoint *without* the response envelope.
  - `GET /api/v1/sample`: Implement to return the standard envelope: `{"value": { "name": "sample" }, "ok": true}`.
- Organize these routes in the `apps/api/routes/v1` directory.

## 5. Documentation Updates
- **Configuration Documentation**: Create `apps/api/docs/configuration.md` detailing the new configuration system, the `Config` struct, and how to use environment variables (e.g., `HYPRSHIP_PORT`).
- **AGENTS.md Update**: Update `apps/api/AGENTS.md` by adding a "Configuration" section requiring agents to keep `apps/api/docs/configuration.md` updated when adding new settings.

## 6. Testing
- **Unit Tests**: Implement unit tests using `net/http/httptest` for the new route handlers (`ping`, `healthz`, `sample`). Ensure asserts are done using `github.com/stretchr/testify/assert`.
- **E2E Tests**: Add e2e tests for the API routes inside the `apps/api/test/e2e` directory using the `// +build e2e` (or `//go:build e2e`) directive.
- **HTTP Files**: Create `.http` files in `apps/api/test/http` to manually test the endpoints (e.g., `api.http`).

## 7. Build/Tasks Integration
- Update or verify that `cast` task definitions (`castfile`) properly support building and testing the newly added configurations. Add cast tasks for running the e2e tests or formatting if missing.
